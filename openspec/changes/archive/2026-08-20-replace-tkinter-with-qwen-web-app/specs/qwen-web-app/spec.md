## Purpose

Defines the local web application workflow for academic literature scoring when the AI provider and models are fixed to Qwen/DashScope.

## ADDED Requirements

### Requirement: Fixed Qwen provider configuration
The system SHALL use Qwen/DashScope as the only AI provider for the web scoring workflow, with base URL `https://dashscope-intl.aliyuncs.com/compatible-mode/v1`, embedding model `text-embedding-v4`, and LLM model `qwen3.6-flash`.

#### Scenario: User starts a scoring job
- **WHEN** the user starts any scoring job from the web interface
- **THEN** the backend uses the fixed Qwen/DashScope base URL and fixed model names for all AI calls

#### Scenario: User views model information
- **WHEN** the user opens the web interface
- **THEN** the interface displays the fixed provider, embedding model, and LLM model as read-only information

### Requirement: Single API key input
The system SHALL accept one user-provided DashScope-compatible API key and SHALL use that key for both embedding and LLM requests.

#### Scenario: User tests API connectivity
- **WHEN** the user submits an API key for connection testing
- **THEN** the system validates the fixed embedding model and reports whether the key can access the fixed Qwen/DashScope configuration

#### Scenario: User omits API key
- **WHEN** the user attempts to test connectivity or start a scoring job without an API key
- **THEN** the system rejects the action with a clear validation message

### Requirement: Model fields are not user editable
The system SHALL NOT expose editable Base URL, embedding model, or LLM model fields in the web interface.

#### Scenario: User configures a run
- **WHEN** the user configures a scoring run in the web interface
- **THEN** the user can configure files, run mode, thresholds, delays, batch preferences, and topic text, but cannot edit provider or model identifiers

### Requirement: Local web job workflow
The system SHALL provide a local web workflow that supports file upload, run creation, status polling, cancellation, and result download.

#### Scenario: User uploads and starts a job
- **WHEN** the user uploads an Excel file, enters a topic, chooses a run mode, and starts processing
- **THEN** the system creates a job and returns a job identifier that can be used to check progress

#### Scenario: User checks job progress
- **WHEN** the frontend requests status for an active job
- **THEN** the backend returns the current progress percentage, status message, log entries, completion state, and any available error message

#### Scenario: User cancels a job
- **WHEN** the user cancels an active job
- **THEN** the backend requests cancellation and the job stops without presenting a completed result

#### Scenario: User downloads completed result
- **WHEN** a job completes successfully
- **THEN** the frontend provides a download action for the generated Excel result

### Requirement: Existing scoring modes are preserved
The system SHALL preserve the existing scoring modes: full embedding plus LLM screening, embedding-only, and LLM-only using an existing score column.

#### Scenario: User selects embedding-only mode
- **WHEN** the user runs embedding-only mode
- **THEN** the output contains embedding scores and indicates that LLM screening was not run

#### Scenario: User selects LLM-only mode
- **WHEN** the user runs LLM-only mode with an input Excel file containing a valid score column
- **THEN** the system skips embedding generation and performs LLM screening using the existing scores

#### Scenario: User selects full mode
- **WHEN** the user runs full mode
- **THEN** the system generates embedding scores, applies threshold routing, runs LLM screening for boundary-score records, and produces the final Excel output

### Requirement: Qwen embedding batch limit enforcement
The system SHALL ensure each embedding API request contains no more than 10 input texts when using `text-embedding-v4`.

#### Scenario: User requests a large batch size
- **WHEN** the user starts a job with a batch preference greater than 10
- **THEN** the backend internally splits embedding requests into provider-compliant chunks of at most 10 texts

### Requirement: Provider-aware embedding cache
The system SHALL prevent embeddings generated by any previous provider or model from being reused for Qwen `text-embedding-v4` scoring.

#### Scenario: Cache contains old embeddings
- **WHEN** a job runs after the system has cached embeddings from a different model or provider
- **THEN** the system does not reuse those old embeddings for Qwen `text-embedding-v4` similarity calculations

#### Scenario: Cache contains matching Qwen embeddings
- **WHEN** a job requests text that was already embedded with the fixed Qwen embedding model
- **THEN** the system may reuse the cached vector for that same model/provider identity

### Requirement: Modern web interface
The system SHALL provide a modern single-page web interface for the scoring workflow.

#### Scenario: User opens the app
- **WHEN** the user opens the local web app
- **THEN** the first screen presents the usable scoring workflow, including file selection, API key entry, run mode, thresholds, topic input, progress, logs, and result actions

#### Scenario: Job state changes
- **WHEN** a job is running, completes, fails, or is cancelled
- **THEN** the interface updates controls and status indicators to reflect the current state without requiring the user to restart the app

### Requirement: Documentation reflects the web workflow
The system SHALL document the fixed Qwen/DashScope configuration and the local web app startup workflow.

#### Scenario: User reads setup instructions
- **WHEN** the user reads the project documentation
- **THEN** the documentation explains how to install dependencies, start the backend and frontend, provide the DashScope API key, run a scoring job, and download results
